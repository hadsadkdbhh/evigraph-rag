\begin{abstract}
Retrieval-augmented generation systems often treat retrieved passages as usable evidence, even when the retrieved context is incomplete, noisy, or numerically under-specified.
We study evidence-state control: a pipeline that converts retrieved candidates into an explicit evidence graph, scores their utility and risk, selects a compact support subgraph, executes table-oriented numerical operations, and verifies generated claims against cited support.
This draft establishes the experimental scaffold for EviGraph-RAG on controlled stress tests and a deterministic 100-example FinQA validation subset.
Current results should be read as diagnostic baselines rather than final benchmark claims.
\end{abstract}

\section{Introduction}

Large language models can fluently answer questions over retrieved documents, but financial and chart/table QA often requires a stricter notion of evidence than lexical relevance.
For example, a retrieved paragraph may mention the right company and year while omitting the denominator needed for a percentage calculation.
This project asks whether retrieval outputs should be treated as \emph{candidate evidence states} rather than final context.

The central hypothesis is that an explicit evidence graph can make RAG more auditable for numerical QA.
Each retrieved item becomes a node with utility, risk, cost, and provenance signals.
The system then selects a support subgraph, expands source context when running oracle-document analysis, executes table operations, and verifies claims against citations.

This skeleton is intentionally conservative.
The current FinQA experiments use a deterministic 100-example validation subset and report three retrieval settings: oracle-document, open BM25, and BM25 with source reranking.

\section{Method}

\subsection{Evidence Graph Construction}

Given a query and retrieved candidates, EviGraph-RAG constructs an evidence graph whose nodes represent text, tables, derived table parses, calculations, and verifier judgments.
Edges record derivation and support relations.

\subsection{Utility-Risk Evidence Selection}

Each node receives a utility score and risk signals such as misleading-risk and contradiction-risk.
The selector chooses a compact support set subject to a node budget and a risk threshold.

\subsection{Table Operation Executor}

For numerical QA, the system executes table operations including row/column selection, sum, difference, ratio, percent change, and average.
Each executed operation returns both a numeric value and a human-readable expression used in the final answer trace.
When deterministic rules fail, an optional LLM numeric planner can propose a structured operation plan; EviGraph-RAG then validates that planned numeric inputs occur in the cited context and executes the operation locally rather than accepting a free-form model answer.

\subsection{Claim Verification}

Generated answers are verified against the selected support graph.
The verifier checks citation presence, source-number consistency, calculation-result consistency, operation-type consistency, and whether calculation row labels are lexically grounded in the query.

\section{Experiments}

\subsection{Datasets}

\textbf{FinQA.} We use a deterministic 100-example validation subset from \texttt{dreamerdeo/finqa}, sampled from the first 100 validation rows with seed 13.
The corpus serializes source pre-text, tables, and post-text to Markdown and excludes gold answers and gold evidence annotations from retrieval.

\textbf{Stress Suite.} We also maintain a synthetic stress suite with official reports and distracting forecast/draft/press evidence.
This suite is used for mechanism debugging, not public benchmark claims.

\subsection{Retrieval Settings}

\textbf{Oracle-doc} constrains retrieval to the gold \texttt{source\_doc} and expands full source context for numerical evidence.
\textbf{Open BM25} retrieves from the full corpus without source metadata.
\textbf{BM25 + source rerank} retrieves broadly and softly promotes candidates whose source matches the known \texttt{source\_doc}; this is an analysis setting, not a deployable open-retrieval claim.

\section{Failure Analysis}

The manifest runner emits a failure report that groups unresolved examples by error category.
Current categories include missing numeric answer, wrong row/operation, additive lookup failures, ratio failures, and percent-operation failures.
Table~\ref{tab:finqa-failure-categories} reports the current full EviGraph failure profile for the 100-example FinQA diagnostic subset.
The largest remaining categories are wrong row/operation selection and unresolved numeric-answer extraction, which are the next engineering targets before scaling to larger benchmark runs.

\section{Conclusion}

EviGraph-RAG reframes RAG as evidence-state control for auditable numerical QA.
The current repository provides a reproducible scaffold, real FinQA subset, retrieval-setting separation, table operation executor, and failure-analysis tooling.
The next step is to strengthen table row/column selection and open-retrieval baselines before making benchmark-level claims.
